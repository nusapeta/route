# Audit antislop 002: kode

Tanggal: 2026-11-08. Cakupan: 29 berkas `.go` (7.056 LOC), 7 binary `cmd/rid-*`, `internal/graph`, `internal/extract`, `deploy/`, `Dockerfile`, `Makefile`, `scripts/`. Mode `after`: temuan bernomor, kode **tidak** diubah sampai nomor disetujui.

Baseline sebelum audit: `go build ./...` exit 0, `go vet ./...` bersih, `go test ./...` lulus semua (`internal/graph` 0,591 s). Jadi semua temuan di bawah adalah cacat yang tidak tertangkap suite saat ini, bukan kerusakan build.

Metode: pembacaan berkas per paket + lima sapuan read-only paralel, lalu setiap klaim HIGH diverifikasi ulang dengan membaca baris yang dikutip atau menjalankan binary. Semua `[runtime]` di bawah adalah keluaran yang saya jalankan sendiri; `[kode]` adalah pembacaan baris yang dikutip.

## HIGH

### H1. Respons 429 dapat di-cache, dan 304 melewati rate limiter
`cmd/rid-server/main.go:341-353`. Header `ETag` + `Cache-Control: public, max-age=3600` dipasang sebelum limiter dan sebelum pencarian rute.

[runtime] Probe `127.0.0.1:18080` (`-rate 2 -burst 1`): respons ketiga dan seterusnya

```
HTTP/1.1 429 Too Many Requests
Cache-Control: public, max-age=3600
Etag: "5031a14c-dbd00c31ae188cde"
Retry-After: 18
```

Memutar ulang request yang sama dengan `If-None-Match: "5031a14c-..."` saat klien sedang ditolak:

```
HTTP/1.1 304 Not Modified
Cache-Control: public, max-age=3600
Etag: "5031a14c-1320782e2f6b1a2b"
```

Mengapa penting: `ETag` dibuat dari parameter rute, bukan dari hasil. Proxy bersama boleh menyimpan 429 selama satu jam (klien lain ikut ditolak), dan klien yang di-throttle tetap dilayani 304 sehingga limiter dapat dilewati dengan tag dari request lama. `Retry-After` + `max-age` saling bertentangan.

Perbaikan: pasang `ETag`/`Cache-Control` hanya pada jalur sukses; kirim `Cache-Control: no-store` untuk 429/5xx; `If-None-Match` hanya dievaluasi setelah limiter.

### H2. `Vary: Accept-Encoding` tidak pernah dikirim, `Content-Encoding: gzip` tetap ada di 304
`cmd/rid-server/main.go:671-685` (`gzipWrap`) memasang `Content-Encoding` tanpa `Vary`.

[runtime]

```
HTTP/1.1 304 Not Modified
Cache-Control: public, max-age=3600
Content-Encoding: gzip
Etag: "5031a14c-cd05d620f1ef2ed9"
```

Tidak ada `Vary` di respons mana pun (juga tidak pada 200). Mengapa penting: `ETag` sama untuk body gzip dan identitas, jadi cache perantara bisa menyajikan byte gzip ke klien yang tidak mengirim `Accept-Encoding: gzip`. 304 yang membawa `Content-Encoding` juga menyalahi RFC 9110 (header representasi pada respons tanpa body).

Perbaikan: `w.Header().Add("Vary", "Accept-Encoding")` di jalur yang sama dengan `gzipWrap`; jangan set `Content-Encoding` pada 304.

### H3. Fingerprint ETag tidak mencakup `-snap`, jadi tag bertahan walau hasil berubah
`cmd/rid-server/etag.go:12-28` men-hash region, `max_route_m`, `eps`, `turn_scale`, `commit`. `maxSnapM` (`-snap`), `-workspace-mb`, dan format graf tidak ikut.

Mengapa penting: komentar di berkas itu menyatakan sidik jari mencakup semua yang menentukan jawaban rute. `-snap` mengubah 422 "no road within snap distance" menjadi rute (atau sebaliknya) tanpa mengubah `ETag`, sehingga klien dengan `If-None-Match` menerima 304 untuk jawaban yang seharusnya sudah berubah.

Perbaikan: masukkan `maxSnapM` (dan `workspaceMB` bila memengaruhi 422 budget) ke input hash; atau hapus klaim kelengkapan dari komentar.

### H4. `ferry_spans` dihitung dari path sebelum `Simplify`, dipakai sesudahnya
`cmd/rid-server/main.go:430-431` menjalankan `pts = graph.Simplify(pts, p.simplify)`, sedangkan `:461-478` memetakan `res.FerrySpans` (indeks ke `Route.Nodes` yang belum dipangkas) ke array yang sudah terpangkas. Bukti kontraknya rusak ada di kode itu sendiri: `off--` dan `if a0 < 0 { a0 = 0 }` adalah penambal manual.

Mengapa penting: dengan `?simplify=1` (atau nilai lain > 0) span ferry menunjuk koordinat yang salah; untuk rute tanpa ferry hasilnya benar hanya karena array span kosong. Penambal `a0 < 0` tidak pernah tercapai bila `off` tidak negatif.

Perbaikan: petakan `FerrySpans` ke geometri hasil `Simplify` di satu tempat (atau simpan `Simplify` sebelum span dipakai), lalu hapus `off--`/clamp.

### H5. `graph.Open` tidak memvalidasi offset bagian; berkas rusak mem-panic, bukan mengembalikan `error`

Mengapa penting: `Open` bertanda tangan `(*Graph, error)` dan seluruh jalur pemanggil memperlakukan kegagalan sebagai error. ### H6. `ErrCanceled` tidak dibungkus, dan timeout bisa muncul sebagai "route too long"
`internal/graph/astar.go:431-432` menjanjikan "returns ErrCanceled (wrapped with the context error)", tetapi `:445-446` dan `:535-536` mengembalikan `ErrCanceled` polos. [kode]

### H8. `rid-snapcheck` memasangkan sampel dengan indeks yang salah, dan menyuntikkan `+Inf` ke statistik
`cmd/rid-snapcheck/main.go:164` menambahkan `segLen` **sebelum** `:167 if !ok { continue }`, sedangkan `nodeErr`/`implErr` ditambahkan sesudahnya (`:171-178`). ### H9. `panic` saat kapasitas workspace kurang, dieksekusi di jalur request

### L8. `only_rules` di `/healthz` bernilai 154, bukan "tidak ada padanan v4"

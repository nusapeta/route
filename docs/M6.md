| lain | Docker **dan user masuk grup `docker`**, `java-latest.osm.pbf` (899 MB) | n/a |

Di laptop pengembangan user belum masuk grup docker (`sudo usermod -aG docker
$USER` lalu logout), jadi `m6-osrm.sh` di sana baru diuji sintaks (`bash -n`),
belum end-to-end. `m6-compare.py` sudah dicoba terhadap `rid-server` lokal:
kolom routeid terisi benar dan OSRM yang mati tercatat sebagai error per baris,
bukan menghentikan run.

Jalankan sendiri: jangan paralel dengan `rid-extract`, load test, atau container
berat. Angka RSS/timing hanya sah kalau mesinnya sepi.

## E1. Baseline OSRM (MLD), ±1-2 jam (mayoritas menunggu)

```bash
cd ~/Projects/routeid
scripts/fetch.sh java                       # kalau pbf belum ada
scripts/m6-osrm.sh extract data/java-latest.osm.pbf   # extract+partition+customize,
                                                      # cetak wall + peak RSS + ukuran
```

De-risk dulu dengan pbf kecil (`maluku-latest.osm.pbf`, ±2 menit) untuk memastikan
Docker/pipeline benar sebelum menunggu extract Jawa.

Lalu nyalakan kedua server **pada mesin yang sama**:

```bash
# terminal 1: OSRM MLD di :5000
scripts/m6-osrm.sh serve data/java-latest.osrm

# terminal 2: routeid di :8080, conc 1 supaya adil per-query
bin/rid-server -graph data/java.graph -addr 127.0.0.1:8080 -conc 1 -rate 0 -timeout 60s

# terminal 3: 600 pasangan identik, diukur bergantian
scripts/m6-compare.py --pairs paper/results/pairs-java.csv \
    --routeid http://127.0.0.1:8080 --osrm http://127.0.0.1:5000 \
    --csv paper/results/m6-osrm-vs-routeid.csv
```

`m6-compare.py` menanyakan routeid (`/route`) dan OSRM
(`/route/v1/driving`) untuk tiap pasangan, bergantian ganjil/genap supaya
peluruhan mesin tidak memihak satu engine, lalu mencetak per bucket:
`ride_p50/p95`, `osrm_p50/p95`, median `dist_delta%`, persentase selisih >10 %,
dan rasio durasi. CSV mentahnya untuk diarsipkan di `paper/results/`.

Catat juga (bukan dari skrip):

| metrik | cara |
|---|---|
| waktu `osrm-extract` / `partition` / `customize` | keluaran `m6-osrm.sh extract` |
| peak RSS tiap tahap | idem (`peak_rss` di skrip) |
| ukuran artefak | `du -sh data/java-latest.osrm*` vs `693 MB` routeid |
| RSS `osrm-routed` idle | `docker stats --no-stream osrm` |
| RSS setelah 600 pasangan | idem, setelah `m6-compare.py` |

### Hasil final (2026-11-10)

OSRM MLD menang latency seperti diperkirakan: pada 332 pasangan cocok, p50
**1,5 ms vs 38,7 ms**, p95 **3,7 ms vs 674 ms**. Routeid menang biaya: artefak
693 MB vs **5,08 GB**, RSS sebelum query 17 MB vs 2,36 GiB, preprocess 28 s vs
250 s. Jarak rute: median |selisih| **0,23%**, p95 **14,49%**, maksimum
**70,44%**; 25/332 >10% dan 8/332 >25%. Gerbang p95 <12% gagal, jadi klaim yang
boleh ditulis tetap **"paling ringan per rute"**, bukan "tercepat" maupun
"paling akurat". Audit §14 menunjukkan p95 jarak berasal dari
perbedaan fungsi biaya (penalti belok, preferensi kelas, `track`), bukan
restriction yang di-skip; 167 `restriction:conditional` tetap batas model.

Penalti belok sudah diimplementasikan dan diukur (§15): default
`-turn-penalty 0.25` (tabel 2/7,5/20 s dibagi empat). 600 pasang E1 diulang pada
0/0,25/1/2x: p95 jarak **tetap 21,12%** di 0,25x (naik 22,02% di 1x), mean
3,60% -> 3,50%, p75 3,03% -> 2,82%, p90 11,20% -> 10,56%, ETA +1,6% median.
Sisa selisih sempat diduga berasal dari tabel kecepatan kelas jalan
(`BACKLOG.md` 16c). Update 2026-11-10: tabel mobil disamakan dengan `car.lua`
OSRM, graph Java dibangun ulang, dan 332 pasangan E1 diukur ulang. Hasilnya
median |selisih| 0,23%, p95 14,49%, maksimum 70,44%; 79/600 gagal
(72 `snap`, 7 `budget`), 189 dibuang filter snap. Pada 79 kegagalan itu OSRM
menempel target dengan median 15,3 km. Gerbang p95 <12% tetap gagal. D4 mengganti metrik primer ke p95 durasi absolut 10,22% secara
eksplisit, bukan mengklaim lulus jarak. Audit 20 outlier menunjukkan akses,
restriksi, dan pilihan rute OSRM ikut menentukan sisa selisih.
Latency antar-run §15 tidak sebanding (mesin dibebani), jadi patokan latency
tetap run final §18 (CSV `e1-osrm-aligned.csv`). Rincian:
`paper/RESULTS.md` §13-§18 dan `docs/PLAN-2026-11-10.md` W3.

Flag yang tersedia: `rid-server -turn-penalty -eps -conc -rate -timeout`,
`rid-route -eps -turn-penalty`, `rid-bench -eps -turn-penalty`.

## E2. Ground truth (butuh referensi independen)

OSRM bukan ground truth: dua-duanya graf OSM, jadi E1 tidak menutup E2.
Butuh salah satu:

| opsi | jumlah | kerja | biaya | kualitas |
|---|---|---|---|---|
| Google Directions API (key) | 200-500 | ±1 jam, otomatis | ~$1 | terbaik |
| Google Maps manual | 60 | ±2 jam manusia | 0 | cukup untuk klaim terbatas |
| tanpa referensi | 0 | tulis limitation | 0 | abstrak tidak boleh klaim "akurat" |

**Keputusan 2026-11-10.** Pemilik memilih opsi tanpa referensi. Tidak ada data
E2 dan tidak ada `GOOGLE_ROUTES_KEY` yang dipakai. E1 tetap perbandingan
antar-engine: p95 jarak 14,49% pada 332 pasangan, 79 gagal (72 snap, 7 budget), D4 mengganti metrik primer ke
p95 durasi absolut 10,22%. Klaim akurasi dicabut dan limitation dicatat di
README, `paper/RESULTS.md` §18, serta `paper/main.tex` §limitation.

Untuk opsi API: taruh key di env `GOOGLE_ROUTES_KEY` (jangan commit), lalu ambil
`distanceMeters` + `polyline` per pasangan dari `paper/results/pairs-java.csv`
(semua bucket ≤50 km, itu batas desain aplikasi). Metrik yang dilaporkan:
selisih jarak relatif per pasangan (median, p95), persentase >10 %, dan daftar
5 kasus terburuk (biasanya restriction/tol/jalan baru).

Target yang boleh dijanjikan: **median <5 %, p95 <12 %**. Kalau gagal, perbaiki
dulu (restriction via-way BACKLOG 16, atau kelas kecepatan) sebelum submit.
